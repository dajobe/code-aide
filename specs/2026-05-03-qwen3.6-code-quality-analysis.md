`console.py`.

## Correctness Risks

### 7. Wrong Return Type Annotation on `run_command`

`console.py:39` declares:

```python
def run_command(...) -> Union[subprocess.CompletedProcess, subprocess.CalledProcessError]:
```

The `CalledProcessError` arm is dead. `subprocess.run` only raises
`CalledProcessError` when `check=True`, and the function's handler re-raises in
that case (`if check: raise`). The `return exc` branch at `console.py:60` is
therefore unreachable in practice.

**Correct fix:** delete the unreachable `except` branch and annotate the return
type as `subprocess.CompletedProcess`. Do not change to `CompletedProcess |
None` — the function never returns `None`.

### 8. Hardcoded Path Separator

`prereqs.py` uses hardcoded `":"` to split `PATH` (TODO.md item 5). Should use
`os.pathsep`. The project classifiers list macOS, Linux, FreeBSD only — not
Windows — so this is a portability nit rather than a runtime bug today, but
still worth fixing for correctness.

## Test Quality Issues

### 10. Unsafe `clear=True` Test Isolation Pattern

`mock.patch.dict(<module>.TOOLS, <fixture>, clear=True)` is used across multiple
test files. If a test raises before the context exits (e.g., the assertion fires
before the `with` block unwinds when the dict has already been mutated),
`mock.patch.dict` does still restore it via the context manager protocol — but
the pattern still has a real problem: **a test that patches `clear=True` but
never restores due to a bug in the `with`/`patch` plumbing leaks to every
subsequent test in the process.** A safer wrapper that snapshots and restores
the dict explicitly (or a fixture using `mock.patch.dict` *without*
`clear=True`) removes the foot-gun.

Affected tests include `tests/test_commands_tools.py:25`,
`tests/test_install.py:78`, and others.

When writing a replacement helper, beware of two pitfalls:

1. The helper must restore **all** keys it modified, not just keys that were
   absent before the patch. `mock.patch.dict` already does this — a custom
   helper that only tracks "new" keys will silently leave existing-key
   modifications in place.
2. For `os.environ` patches, prefer `monkeypatch.setenv` (pytest) or plain
   `mock.patch.dict(os.environ, ..., clear=False)` over a home-grown wrapper.

## Configuration & Tooling Issues

### 13. Incomplete pytest Configuration

`pyproject.toml` (lines 44-45):

```toml
[tool.pytest.ini_options]
testpaths = ["tests"]
```

Missing:

- `filterwarnings` — deprecation warnings silently ignored
- `markers` — custom markers like `network` are undeclared, so
  `--strict-markers` cannot be enabled

### 14. No Logging Infrastructure

The codebase has zero `import logging` calls in `src/code_aide/`. This matters
because:

- The `console.py` helpers (`info`, `error`, `warning`, `success`) print
  directly to stdout/stderr with ANSI colors. There's no way to redirect,
  suppress, or structure them.
- Any future fix that replaces `except: pass` with `_logger.debug(...)` needs a
  `logging.basicConfig(...)` call wired to `--verbose` / `--debug` flags in
  `entry.py`, or it will silently log to nowhere.
- A `--debug` flag would let users diagnose package-detection failures without
  code changes.

### 15. Missing Standard Dev Tooling

`pyproject.toml` `[dependency-groups].dev` lists `pytest`, `pytest-xdist`,
`black`, `ruff`. Missing per the project's stated Python convention: **`mypy`**.
Type annotations exist throughout the codebase but are never checked.

### 16. Mutable Global `TOOLS` Dict

`TOOLS` in `code_aide.constants` is a plain `dict` populated at import time from
the bundled JSON. Any code path (or test) can mutate it, which is the root cause
of the `clear=True` test-isolation hazard (Issue #10). Wrapping it in
`types.MappingProxyType` at module load would make the mutation impossible at
runtime — tests that need a different fixture would have to use proper patching,
and accidental production mutation would fail loudly.

### 17. Incomplete Tool-Definition Documentation

The `README.md` and bundled tool JSON files do not document several fields that
`install.py` / `detection.py` / `operations.py` rely on:

- `freebsd_port` and `freebsd_pkg_repo` (used in `install.py:298-328`,
  `detection.py:105-107`)
- `version_args` (default `["--version"]`, used in `status.py:449`)
- `install_script_path_prepend` (used in `install.py:106`, `operations.py:232`)

Adding new tools requires reading the source to discover these.
